# CAN 收发设计说明

> 本文档描述当前 `can_bridge` 包中 CAN 数据收发（发送 / 接收）的总体设计思路与实现约定，不涉及具体 CAN 报文结构（字段位定义、报文 ID 规划等见 README / 代码）。

## 1. 概述

`can_bridge` 是 ROS 上层（决策 / 控制）与底层车辆总线（CAN）之间的**唯一数据通道**，承担两类职责：

1. **发送路径**：订阅 ROS 控制命令话题，把油门 / 转向指令下发到 CAN 总线。
2. **接收路径**：从 CAN 总线读取外部（遥控 / 裁判系统）下发的状态，用于**门控发送使能**，保证车辆只有在被允许启动时才输出真实控制量。

整体设计遵循"**接收驱动状态、发送受控执行**"的原则：CAN 接收决定"能不能动"，ROS 命令决定"动多少"。

## 2. 总体架构

```
┌─────────────────────┐   /control/test_mode/   ┌──────────────────────┐
│  上层控制节点        │ ───────control_command──▶│      CanBridge       │
│  (detour_test 等)   │   ControlCommand.msg     │   (can_bridge_node)  │
└─────────────────────┘                          │                      │
                                                 │  ┌──────────────┐    │
                                                 │  │  CanReceiver │◀───┼── CAN 总线 (接收)
                                                 │  └──────┬───────┘    │
                                                 │         │ game_mode/ │
                                                 │         │ flag       │
                                                 │         ▼            │
                                                 │  使能门控 (enabled_)  │
                                                 │         │            │
                                                 │  ┌──────────────┐    │
                                                 │  │  CanSender   │────┼──▶ CAN 总线 (发送)
                                                 │  └──────────────┘    │
                                                 └──────────────────────┘
```

**分层设计**：

- **节点层（`CanBridge`）**：负责编排——轮询接收、维护使能状态、在 ROS 回调里执行发送。它不关心报文如何编码、socket 如何管理。
- **设备层（`CanSender` / `CanReceiver`）**：各自封装一个 SocketCAN 原始套接字，只负责"把数据放进 CAN 帧 / 从 CAN 帧取出数据"，不关心业务逻辑。

这种职责划分使业务逻辑（门控、零输出兜底）与总线细节（socket、字节序、设备名）解耦，便于单独替换设备层（例如换成其他总线协议）。

## 3. 模块职责划分

### 3.1 CanBridge（节点层，业务编排）

维护两个内部状态：

| 状态 | 含义 |
|---|---|
| `enabled_` | 是否允许输出真实控制量，由接收到的 flag 决定 |
| `game_mode_` | 最近一次收到的游戏 / 比赛模式，随报文透传 |

核心逻辑（[can_bridge_node.cpp](file:///d:/桌面文件/编程实践/detour/src/can_bridge/src/can_bridge_node.cpp#L19-L33)）：

- `update()`：从 `CanReceiver` 读取 `game_mode_` 与 `flag`，将 `enabled_` 置为 `flag == 0x01`。
- `sendCommand(throttle, steering)`：**先门控、后发送**——`enabled_` 为真时原样发送 ROS 命令，否则强制替换为 `(0, 0)` 后仍照常发送。

### 3.2 CanSender（发送设备层）

职责：

- 创建并维护一个 SocketCAN 原始套接字（`PF_CAN / SOCK_RAW`）。
- 打开接口、绑定 `can0`，失败时降级（`sock_ = -1`），后续 `send()` 直接返回 `false`。
- 提供 `send(throttle, steering, flag)`：完成 **float → 定标整型** 的数值变换，并组装为一帧 CAN 报文写回总线。

### 3.3 CanReceiver（接收设备层）

职责：

- 创建 SocketCAN 套接字并**设置为非阻塞**（`O_NONBLOCK`）。
- 提供 `receive(game_mode, flag)`：尝试读一帧，读到则解析出 `game_mode` 与 `flag`，返回 `true`；无数据或错误返回 `false`。
- 非阻塞是本层最关键的设计决策（详见 §6）。

## 4. 数据流与时序

### 4.1 接收路径（轮询驱动，50 Hz）

主循环（[can_bridge_node.cpp](file:///d:/桌面文件/编程实践/detour/src/can_bridge/src/can_bridge_node.cpp#L53-L58)）以 `ros::Rate(50)` 节奏运行：

```
while (ros::ok()) {
    bridge.update();      // 非阻塞读取 CAN，刷新 enabled_ / game_mode_
    ros::spinOnce();      // 处理订阅回调，触发发送
    rate.sleep();         // 维持 50 Hz 节拍
}
```

- 接收是**主动轮询**而非阻塞等待，保证主循环节拍稳定，不受 CAN 报文到达节奏影响。
- 50 Hz 轮询对"启停标志"这类低频状态足够；标志变化最长延迟一个周期（20 ms）被感知。

### 4.2 发送路径（回调驱动，随命令频率）

发送由 ROS 订阅回调触发：每收到一条 `ControlCommand` 就执行一次 `sendCommand()`。发送频率因此**跟随上游控制命令发布频率**，不额外节流。

两条路径的节奏差异是刻意设计的：

- **接收**：低频、周期性轮询，只关心"最新状态"（last-value-wins）。
- **发送**：高频、事件驱动，紧跟控制指令流，避免在网关上人为引入延迟。

## 5. 安全设计

发送使能门控是整个设计中最重要的安全机制，共三层防护：

### 5.1 启动门控

- 只有收到 `flag == 0x01` 时 `enabled_` 才为真，车辆才允许输出非零油门 / 转向。
- 任何其他 flag 值、或从未收到报文（初始 `enabled_ = false`），一律视为"不允许启动"。

### 5.2 零输出兜底

即使收到 ROS 命令，只要未使能，`sendCommand()` 也会强制以 `(0, 0)` 发送：

```cpp
float t = enabled_ ? throttle : 0.0f;
float s = enabled_ ? steering : 0.0f;
```

这保证"允许动"与"实际动"严格一致，且未使能期间总线仍持续收到明确的安全值（而非静默停发）。

### 5.3 退出前清零

主循环结束后调用 `sendCommand(0.0f, 0.0f)`，在节点退出时向总线发送最后一帧零命令，尽量让车辆停在安全状态。

### 5.4 防阻塞

接收采用非阻塞读，避免 CAN 无数据时卡住主循环，从而保证门控逻辑始终以固定节拍运行。

## 6. 线程模型与并发

- 节点为**单线程**：`ros::spinOnce()` + 轮询，无锁、无共享资源竞争。
- 发送发生在 ROS 回调线程上下文（即主循环内，因 spinOnce 由主循环调用），与接收轮询天然串行，不存在并发写 socket 的问题。
- 设计上**刻意避免多线程**：CAN 数据量小、实时性要求不高，单线程足以满足，且显著降低调试复杂度。

**注意的边界**：如果未来将接收改为独立线程（阻塞读），则 `enabled_` / `game_mode_` 与发送回调之间需要同步（mutex / atomic），当前设计不涉及此问题。

## 7. 错误处理与容错

### 7.1 设备不可用时的降级

- 套接字创建、接口绑定任一失败，`sock_` 置为 `-1`。
- 此后 `send()` / `receive()` 一律返回 `false`，节点**静默降级**运行：接收不到使能 → `enabled_` 恒为 `false` → 只发零命令。
- 这是"故障即安全"（fail-safe）的体现：CAN 通道不可用时，车辆不可能被误驱动。

### 7.2 无超时 / 断线检测

当前实现**没有**超时看门狗：若 CAN 总线上停止出现使能报文，`enabled_` 会停留在最后一次收到的值。若最后一条是 `flag == 0x01`，车辆会保持使能直至下次收到报文。这是当前设计的一个已知局限（见 §11 改进建议）。

### 7.3 数据变换溢出

数值变换（§8）采用截断式转换，输入超出 `[-1, 1]` 时会被钳位到 16 bit 边界，不产生非法报文。

## 8. 数据变换约定

- 业务层浮点范围：油门 / 转向角均为 **`[-1.0, 1.0]`**（见 [ControlCommand.msg](file:///d:/桌面文件/编程实践/detour/src/fsd_common_msgs/msg/ControlCommand.msg)）。
- 总线侧为无符号 16 bit 定标值，线性映射：`value = (x + 1.0) * 32767.5`。
- 变换集中在 `CanSender::send()` 内完成，业务层始终以归一化浮点传递，避免在多个位置各自换算造成不一致。

## 9. 参数与可配置性

| 配置项 | 当前实现 | 备注 |
|---|---|---|
| CAN 设备名 | `can0` 硬编码 | 真实硬件与 vcan 调试均用同一名称，靠系统侧建接口 |
| 报文 ID | `0x456` 硬编码（类默认参数） | 头文件与 launch 中均有声明意图，但代码未真正读取参数 |
| 控制话题 | 硬编码 `/control/test_mode/control_command` | 与 launch 中声明的 `/control/pure_pursuit/control_command` 不一致，以代码为准 |
| 轮询频率 | `50 Hz` 硬编码 | 与接收 / 门控刷新节拍绑定 |

当前"配置"主要通过**修改源码 + 系统侧建接口**实现。launch 文件已预留参数声明，说明参数化是预期方向，尚未落地（见 §11）。

## 10. 调试与测试手段

设计上预留了两条独立调试路径（详见 README）：

1. **全虚拟链路**：`vcan0` + `cansend` / `candump` 模拟总线，配合 `rostopic pub` 手动注入命令，可完整走通"使能门控 → 零输出 → 放行输出"各状态。
2. **socketcan_bridge 桥接**：将 vcan 转发为 ROS 话题，便于在 ROS 生态内直接观测报文。

调试要点：

- `cansend vcan0 456#0101`（使能）与 `#0100`（禁止）可分别验证门控开 / 关行为；
- `candump` 可验证未使能期间总线持续收到 `(0,0)`，符合安全设计预期。

## 11. 设计权衡与改进建议

### 优点

- **分层清晰**：节点层 / 设备层分离，业务与总线细节解耦。
- **安全兜底完备**：门控 + 零输出 + 退出清零，故障方向均收敛到"不动"。
- **单线程、简单可靠**：无并发问题，易读易维护。
- **数值变换收敛在一处**：映射规则唯一，避免散落实现。

### 已知局限

1. 无使能报文**超时看门狗**，总线断线后使能状态可能残留。
2. 接收未按报文 ID 过滤（`SOCK_RAW` 全量接收），解析位置固定取前两个字节，依赖单报文假设。
3. 配置硬编码，launch 参数与实际代码不一致，跨环境（真车 / 仿真 / vcan）切换需要改码。
4. 发送失败（`write` 返回失败）未做计数 / 告警，总线错误不可见。
5. socket 打开失败静默降级，运维上无任何日志或诊断输出。

### 改进方向（优先级从高到低）

1. **使能超时看门狗**：记录最近一次有效接收时间，超时强制 `enabled_ = false` 并发零。
2. **参数化**：从 ROS 参数服务器读取设备名、报文 ID、控制话题、轮询频率，消除硬编码与 launch 不一致。
3. **接收过滤**：按预期 ID 过滤（`setsockopt(CAN_RAW_FILTER)`），降低串扰误触发风险。
4. **诊断输出**：节点启动时打印 socket 初始化结果；发送失败计数并 `ROS_WARN`。
5. **发送使能独立于数据**：当前 `flag` 与 `game_mode` 共用一个报文 / 一个通道，可考虑将启停标志单独成帧或独立节点，明确权限边界。
